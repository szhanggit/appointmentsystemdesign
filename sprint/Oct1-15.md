# Sprint Plan — Oct 1–15, 2026: Customer Registration/Login, End to End

**Goal:** a live demo, by Oct 15, of the real flow: a customer registers → gets an SMS (or email) code → confirms → logs in → can request a password reset and set a new password. Everything behind it — Terraform-provisioned infra, Postgres schema, C# backend, Angular frontend, automated tests, Docker, local dev environment, CI/CD — exists to make that demo real, not staged.

**Source of truth:** `usercasestudy/user-registration-workflow.md` (endpoints, sequence diagrams, schema) and `usercasestudy/groway-v1-architecture.md` (module boundaries, auth scheme, Redis/SQS conventions). This plan does not redesign anything in those documents — it sequences *building* what they already specify.

**Working days in range:** Thu Oct 1, Fri Oct 2, Mon–Fri Oct 5–9, Mon–Thu Oct 12–15 = **11 working days**, solo.

---

## 0. Scope decisions (read this before objecting to what's missing below)

`user-registration-workflow.md` designs more than 11 days can safely build, test, and wire into CI from a standing start. To protect the one thing that actually matters — a real, working demo on Oct 15 — this sprint deliberately **narrows** scope. Everything cut here is still in the design doc; it's just not *this* sprint.

| In scope this sprint | Deferred (next sprint) | Why deferred |
|---|---|---|
| Register: `POST /auth/register` + `/register/confirm` (phone/SMS, §6.1) | Google login (§6.4) | OAuth Hosted UI redirect handling is a full slice of its own; not on the demo's critical path |
| Login: **email + password** (§6.3) | Phone + SMS-code login (§6.2) | Needs 3 Cognito Lambda triggers (`DefineAuthChallenge`/`CreateAuthChallenge`/`VerifyAuthChallengeResponse`) — real serverless infra, real extra Terraform, real extra failure modes. The demo's "login successfully" is satisfied by email+password; phone-OTP login is additive, not required |
| Forgot / reset password (§6.5) | MFA (`login/mfa`, §6.3) | Not needed until MFA is actually enabled on the pool |
| `GET /users/me` (thin, to prove the session works) | Deferred email verification (§6.6) | Nice-to-have, not demo-critical |
| `customer.customers` + `customer.customer_activity_log` (§7.1) | M2M partner API (§9) | No partner exists yet to consume it |
| One Gateway + Customer Module only | Store Module, Admin Module, other two Cognito Pools | Nothing in this sprint's demo touches them |
| ECS Fargate (or App Runner) for the deployed dev environment | EKS + KEDA (architecture doc §8) | Provisioning and debugging a K8s cluster is its own multi-day project; a single Fargate service is enough to prove the pipeline and host a demo. Migrating to EKS later doesn't change the application code — this is an infra-only swap when Store/Admin modules justify the jump to KEDA-scaled consumers |
| SQS queue + a basic consumer (batched insert into `customer_activity_log`) | KEDA autoscaling of that consumer | Same reasoning — one fixed-size consumer task is enough to prove the pipeline works |

**If Oct 15 arrives and something has to slip, slip in this order:** (1) CI/CD polish → (2) integration test breadth → (3) Terraform for anything past Cognito/RDS/SQS/ECR → (4) unit test breadth. **Never slip the demo path itself** (register → confirm → login → forgot/reset).

## 1. Architecture-for-this-sprint (concrete, not aspirational)

```
Angular SPA (localhost:4200 dev / S3+CloudFront later)
        |
        v
Groway.Gateway  (ASP.NET Core, /api/customer/* only this sprint)
        |  in-process call (architecture doc §4)
        v
Groway.Customer  (Application / Domain / Infrastructure)
        |                          |                    |
        v                          v                    v
Amazon Cognito              PostgreSQL              Amazon SQS
(Customer User Pool)     (customer schema)      (customer-activity-log)
        |                                              |
        v                                              v
   Amazon SNS (SMS)                          one fixed-size consumer
```

Solution layout (per architecture doc §3, trimmed to what this sprint needs):

```
src/
├── Groway.Gateway/            -- ASP.NET Core host, route groups, DTO mapping only
├── Groway.Customer/           -- Application, Domain, Infrastructure (internal types)
├── Groway.Shared/             -- CallerContext, OpaqueSessionAuthHandler, SQS helper, Redis session helper
tests/
├── Groway.Customer.UnitTests/         -- xUnit, Application layer, Cognito mocked
└── Groway.Customer.IntegrationTests/  -- xUnit, WebApplicationFactory + Testcontainers (Postgres)
frontend/
└── groway-web/                -- Angular app: register, confirm, login, forgot/reset pages
infra/
└── terraform/
    ├── bootstrap/              -- S3 state bucket + DynamoDB lock table (applied once, by hand)
    └── environments/dev/       -- Cognito, RDS, SQS, ECR, ECS Fargate, networking
```

**`Groway.Customer.Contracts` is skipped this sprint.** Nothing calls Customer Module from another module yet (Store/Admin don't exist), so there's no consumer for a contracts assembly to serve. Add it the day a second module needs to call in — not before (architecture doc §10: don't extract/abstract for a hypothetical future need).

**Testability decision, made now so it doesn't get discovered on day 8:** wrap Cognito behind `ICognitoIdentityService` (methods: `SignUpAsync`, `ConfirmSignUpAsync`, `InitiateAuthAsync`, `ForgotPasswordAsync`, `ConfirmForgotPasswordAsync`). Production implementation calls `AWSSDK.CognitoIdentityProvider`. Integration tests use a **fake** in-memory implementation — Cognito has no local emulator and no Testcontainers image, so integration tests exercise real Postgres (via Testcontainers) but a fake Cognito. A small number of true end-to-end smoke checks against the real *dev* Cognito pool happen manually (§8) and, later, in a separate slow CI job — not on every PR.

## 2. Day-by-day plan

### Day 1 (Thu Oct 1) — Terraform bootstrap + Cognito + repo skeleton

- `infra/terraform/bootstrap/`: S3 bucket (versioned, encrypted) + DynamoDB table for Terraform remote state/locking. Apply this once, by hand, with local state (chicken-and-egg — this is the one Terraform config allowed to use local state).
- `infra/terraform/environments/dev/`: backend block pointing at the bootstrap bucket/table. AWS provider configured for **OIDC federation from GitHub Actions** (no long-lived IAM access keys in CI — set this up right the first time, not retrofitted in week 2).
- Cognito User Pool (Customer Pool): email + phone attributes, phone as an alias, auto-verified phone, `USER_PASSWORD_AUTH` explicit flow enabled, **"prevent user existence errors" ON** (architecture doc / design doc §6.2 recommendation), password policy per Cognito defaults for now. User Pool Client: no client secret needed if only server-side SDK calls it directly with `SecretHash` computed server-side — decide and note whichever `GenerateSecret` setting you pick, since it changes every Cognito call's signature.
- **SNS SMS sandbox check, day 1, not day 10:** a fresh AWS account's SNS SMS starts in sandbox — only pre-verified phone numbers can receive SMS. Verify your own test number today; file the production-access request today too if it's not already granted (approval can take days — this is the single most likely thing to silently block the demo if left late).
- Repo skeleton: solution file, the four projects above, empty `Program.cs` in `Groway.Gateway` that at least boots and serves `/health`.
- `dotnet new gitignore`, root `README.md` stub pointing at this plan.

**End-of-day check:** `terraform apply` succeeds against a real AWS account; a Cognito User Pool exists in the console; `dotnet build` succeeds on an empty solution.

### Day 2 (Fri Oct 2) — RDS + SQS + ECR, database schema, EF Core migration

- Terraform: RDS Postgres (single `db.t4g.micro` instance is enough for dev — no Multi-AZ, no read replica), `customer` schema created via a migration, not Terraform. SQS queue `customer-activity-log` + a DLQ. ECR repository for the backend image.
- `Groway.Customer.Infrastructure`: `CustomerDbContext`, EF Core model for `customer.customers` and `customer.customer_activity_log` exactly as specified in `user-registration-workflow.md` §7.1 (including the `chk_event_type` CHECK — EF Core needs a raw-SQL migration snippet for CHECK constraints, they don't come from the fluent API directly).
- First EF Core migration, applied against the real dev RDS instance once, to prove connectivity end to end (Terraform → RDS → EF Core migration → real tables exist).

**End-of-day check:** `psql` against the dev RDS instance shows `customer.customers` and `customer.customer_activity_log` with the right columns/constraints.

### Day 3 (Mon Oct 5) — Backend skeleton: auth scheme, Redis session, walking-skeleton register endpoint

- `Groway.Shared`: `CallerContext` record, `OpaqueSessionAuthHandler` + `CustomerSession` scheme registration (architecture doc §6.3), Redis connection setup (ElastiCache for dev — or, to save a day of Terraform, a single Redis container reachable from the dev Fargate task; **decide today**, don't let this float).
- `ICognitoIdentityService` interface + real AWS SDK implementation.
- `POST /api/customer/auth/register` — thinnest possible version: call Cognito `SignUp`, return 200. No DB write yet, no SQS yet. This is the "walking skeleton" — prove the request makes it from Angular-shaped JSON through the Gateway into Cognito and a real SMS goes out, before building anything else on top.

**End-of-day check:** a `curl`/Postman call to the real dev environment (or locally against dev Cognito) triggers a real SMS to your verified test number.

### Day 4 (Tue Oct 6) — Complete registration: confirm, DB write, activity log

- `POST /api/customer/auth/register/confirm` — `ConfirmSignUp`, then `InitiateAuth(USER_PASSWORD_AUTH)` to log the new customer in immediately (per §6.1's diagram), `INSERT INTO customer.customers`, fire-and-forget `SendMessage` to `customer-activity-log`.
- The SQS consumer: a plain long-running background service (`BackgroundService` in the same or a separate small worker project) doing batched `ReceiveMessage`/`INSERT`/`DeleteMessageBatch` per architecture doc §8 — no KEDA this sprint (§0), so this just runs as one fixed task.
- Opaque session token issuance: on successful confirm, `SET session:<hash> ...` in Redis, return it to the caller.

**End-of-day check:** full register → SMS → confirm → session token round trip works against the real dev Cognito pool and dev RDS.

### Day 5 (Wed Oct 7) — Login (email+password) + `GET /users/me`

- `POST /api/customer/auth/login` (§6.3, `USER_PASSWORD_AUTH` only — no MFA branch this sprint).
- `GET /api/customer/users/me` reading the session out of Redis via `CustomerSession` — this is what actually *proves* the auth scheme and session plumbing work, not just that Cognito returned a token.
- Unit tests start now, not after the feature is "done" — write them alongside Day 3–5's handlers as you go (see §3 for what "done" means for tests this sprint).

**End-of-day check:** register → confirm → login → `GET /users/me` returns the right profile, end to end, locally.

### Day 6 (Thu Oct 8) — Forgot / reset password

- `POST /api/customer/auth/password/forgot` (`ForgotPassword`) and `POST /api/customer/auth/password/reset` (`ConfirmForgotPassword`), per §6.5 exactly — including the deliberately generic "if that account exists, a code was sent" response regardless of whether the email/phone matched anything.
- Manually verify where Cognito actually sends the reset code by default (email vs. SMS, depending on which attribute is marked as the recovery mechanism on the pool) — confirm this matches what the demo script (§7) will show, adjust the User Pool's account-recovery setting via Terraform if not.

**End-of-day check:** full loop — register → confirm → login → forgot → reset → login again with the new password — works locally against real dev Cognito/RDS.

**This is the demo-critical path, fully working, with two working days of buffer left before Oct 15 for everything else.**

### Day 7 (Fri Oct 9) — Dockerfile + local dev environment (docker-compose)

- Multi-stage `Dockerfile` for `Groway.Gateway` (SDK build stage → `aspnet` runtime stage).
- `docker-compose.yml` for local dev: Postgres container (local schema, migrated on container start), backend container (or `dotnet run` outside compose — either is fine, pick one and document it), Angular dev server via `ng serve` (not containerized for dev — faster iteration). **Cognito, SQS, SNS stay real AWS even for local dev** — there's no local emulator worth the setup time this sprint; `appsettings.Development.json` points at the real dev Cognito Pool ID / SQS queue URL, `docker-compose.yml`'s Postgres is the only thing actually local. Document this explicitly in the README so it isn't a surprise.
- `.env.example` / `appsettings.Development.json.example` checked in; real secrets stay out of git (AWS credentials via the developer's own local AWS CLI profile, not embedded config).

**End-of-day check:** a fresh clone + `docker-compose up` + `dotnet run` + `ng serve` gets a new developer to a working local register/login flow with no manual AWS console steps beyond having an AWS CLI profile configured.

### Day 8 (Mon Oct 12) — Angular frontend

- Four screens/components: register (name/email/phone/password), confirm (SMS code entry), login (email/password), forgot/reset password (two-step: request code, then submit code + new password).
- A minimal `AuthService` in Angular wrapping the four/five backend calls, storing the opaque session token (e.g. in memory + a refresh-safe store — don't overbuild this; a simple `localStorage` token for the demo is fine, this isn't the sprint to design a full token-refresh strategy).
- No design polish budget this sprint — functional, readable forms with real validation messages (especially Cognito's own error messages surfaced sensibly, e.g. "password doesn't meet requirements," "code expired").

**End-of-day check:** the whole demo path works by clicking through the actual Angular app, not just via `curl`.

### Day 9 (Tue Oct 13) — Integration tests

- `WebApplicationFactory<Program>` host wired to: Testcontainers-managed Postgres (real DB, real migrations run against it at test-fixture startup) + the fake `ICognitoIdentityService` (§1).
- Cover, as actual integration tests (not just unit tests with everything mocked): register → confirm → DB row exists with the right fields; login success and failure (wrong password); forgot → reset → login with new password succeeds, login with old password fails.
- Fill in any unit-test gaps from Days 3–6 that got deferred under time pressure — this is the backstop day for that, not a place to start test-writing from zero.

**End-of-day check:** `dotnet test` runs the full suite (unit + integration) locally and in a clean checkout, no flakiness from container startup ordering.

### Day 10 (Wed Oct 14) — GitHub Actions CI/CD

- `ci.yml`: on PR — restore, build, `dotnet test` (integration tests need Docker-in-Docker for Testcontainers; GitHub-hosted runners support this natively), Angular `npm ci && npm run build && npm run lint`.
- `deploy.yml`: on merge to `main` — build and push the backend image to ECR (tagged with the commit SHA), `terraform plan` posted as a PR comment on infra PRs, `terraform apply` (manual approval gate via a GitHub Environment protection rule — never auto-apply to the AWS account this sprint), then a simple `ecs update-service --force-new-deployment` (or Fargate task definition revision) to roll the new image out. No blue/green, no canary — that's over-engineering for a dev environment demo.
- OIDC role assumption (configured Day 1) used here — confirm no access keys ever entered a GitHub secret.

**End-of-day check:** a real PR merge to `main` results in a new image running in the dev ECS service, automatically, with no manual `docker push`.

### Day 11 (Thu Oct 15) — Buffer, bug bash, demo rehearsal

- No new features. Fix whatever the previous 10 days surfaced.
- Run the exact demo script (§7) twice, on the actual deployed dev environment (not just locally) — once by you, once by someone else following the script cold, to catch anything that only makes sense inside your own head.
- Reset the demo's test data/Cognito test user to a clean state before the real demo.

## 3. What "done" means for tests this sprint (don't gold-plate, don't skip)

- **Unit tests (xUnit):** every Application-layer handler (register, confirm, login, forgot, reset) has at least a success-path test and its most important failure-path test (e.g. duplicate email on register, wrong password on login, expired code on reset), with `ICognitoIdentityService` mocked (Moq or NSubstitute — pick one, don't mix). Not exhaustive edge-case coverage — that's a backlog item, not an Oct 15 requirement.
- **Integration tests (WebApplicationFactory + Testcontainers):** the four flows in §2 Day 9, against a real Postgres, fake Cognito. This is what actually catches EF Core mapping mistakes and route-wiring mistakes that mocked unit tests can't.
- **No load/performance tests, no security-scanning pipeline step, no contract tests** this sprint — explicitly out of scope, not forgotten.

## 4. Risks and mitigations

| Risk | Mitigation |
|---|---|
| SNS SMS sandbox blocks real SMS delivery | Verify a test number **Day 1**; file production-access request **Day 1** (approval isn't instant) |
| Cognito has no local emulator/Testcontainers image | Abstract behind `ICognitoIdentityService` (§1) from the start — don't discover this gap on Day 9 |
| EF Core CHECK constraints don't come from the fluent API | Handle via a raw-SQL migration operation, planned for explicitly on Day 2, not discovered as a migration failure later |
| 11 days is genuinely tight for infra + backend + frontend + tests + CI/CD from zero | Day 6 is the "demo path fully works, locally" checkpoint, with Days 7–11 as infra/polish/CI buffer — if Day 6 slips, cut from Day 10 (CI/CD) and Day 9 (test breadth) first, per §0's ordering, never from the demo path |
| Terraform state corruption / conflicting local applies | Remote state (S3+DynamoDB) from Day 1, never local state past the bootstrap step |
| Real AWS costs accumulating in a dev account across the sprint | `db.t4g.micro`, no Multi-AZ, Fargate (not EKS) — matches earlier dev-cost-estimate work; tear down or stop resources between work sessions if cost becomes a concern, Terraform makes re-creating cheap |

## 7. Demo script (rehearse this exact sequence on Day 11)

1. Open the Angular app, register a brand-new customer (real name/email/phone/password).
2. Show the real SMS arriving on the test phone.
3. Enter the code, land logged in, show `GET /users/me`'s profile data rendered on screen.
4. Log out.
5. Log back in with email + password.
6. Click "forgot password," show the reset code arriving (email or SMS, per whatever Day 6 confirmed Cognito is configured to use).
7. Set a new password, log in with the new one — and show the *old* password now fails.
8. (Stretch, if time allows) Open the RDS table and the CloudWatch/SQS console briefly to show the activity log actually landed, not just that the UI looked right.
