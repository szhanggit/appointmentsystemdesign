# Create Appointment Transaction（2026-09-29 v1 草案）

本地 spec，供 Claude Code 实现。**只存本地，不上 GitHub。**

定位：`availability-slot-engine.md` 只算"哪些时间可约"，本篇拥有"创建预约"这个动作本身——请求/响应契约、状态机、slot 二次校验、防 double-booking、幂等、quota 同事务、并发语义。读本篇之前先读 slot engine（§8 的三个未决问题在本篇决议）。

基线事实（不再论证，直接引用）：
- `store.appointments` 是单人单块模型：头挂 `staff_id`（人级）+ `starts_at/ends_at`；多服务走 `appointment_items`，由**同一人**背靠背完成（`store-onboarding-v1-design.md` §4）。
- 预约占用读**头**，buffer 用**头上的快照**（slot engine §4 Step 5）。
- Buffer 快照规则（onboarding §4 已定）：`buffer_before_minutes` = 第一个服务的 Bb，`buffer_after_minutes` = 最后一个服务的 Ba。
- Quota：`BillingQuotaService.TryConsumeAsync(storeId)`，条件 upsert 原子操作；`is_test` 跳过 quota（`groway-billing-workflow.md` §4.2）。
- 鉴权：写操作当且仅当 `storeId ∈ caller.AuthorizedStoreIds`；跨店资源一律 404 不 403。
- 时间：对外一律门店本地 `YYYY-MM-DDTHH:mm:ss`，内部比较转 UTC（沿用 slot engine 约定）。

## 0. 本篇的裁决（先看结论）

1. **`pending` 占用 slot，TTL 15 分钟**（新增 `booking_settings.pending_hold_minutes`，默认 15）。理由：`pending` 不占位则 `auto_confirm=false` 形同虚设——客户"占住"的东西必须真实存在，否则确认时大概率只剩 409。
2. **防 double-booking 靠 PostgreSQL exclusion constraint**，不是 advisory lock。理由：锁是进程级的，进程重启/多实例就破；约束是数据级的，永远成立。`btree_gist` 扩展。
3. **允许 guest 预约**（name + phone 必填）。理由：spa 试点低摩擦优先；`customer_id` 改为 nullable，另加 `guest_*` 列。
4. **"任意员工"由服务端确定性指派**：取 slot engine 返回的 `staff_ids` 顺序第一个。理由：v1 可预测比"智能"重要；负载均衡是 v2 的事。
5. **多服务背靠背排**：服务 i+1 的开始 = 服务 i 结束 + `max(buffer_after_i, buffer_before_{i+1})`。理由：与已定的头快照规则（Bb 取首、Ba 取末）自洽。
6. **改期 = 原地 UPDATE**（同一 id，重校验），不是 cancel + create。理由：cancel 仍然计 quota（既定规则），cancel + create 会让一次改期吃掉 2 个 quota；原地改只吃 1 个。
7. **confirmed 超过 `ends_at` 由 sweeper 自动标 completed**。理由：员工会忘；completed 必须可信，否则以后的报表/AI 都建立在脏数据上。
8. **`payment_required=true` 时创建走 pending + 支付挂钩**，支付提供商对接另起文档。理由：不为一个还没选型的 provider 阻塞 v1。

## 1. 状态机

```
pending --(auto_confirm=true，直接)--> confirmed
pending --(auto_confirm=false，员工在 back-office 点确认)--> confirmed
pending --(payment_required=true，支付成功)--> confirmed
pending --(TTL 到，sweeper)--> expired
pending --(客户/员工取消)--> cancelled
confirmed --(取消；客户受 cancel_threshold_hours 约束)--> cancelled
confirmed --(员工标记)--> no_show
confirmed --(sweeper：ends_at 已过)--> completed
```

- `expired` / `cancelled` / `completed` / `no_show` 为终态。
- 只有 `pending` 和 `confirmed` 占用员工时间（exclusion constraint 的判定依据，§5）。
- `auto_confirm=true`（默认）：创建即 `confirmed`，没有 `pending` 中间态。
- `auto_confirm=false`：创建为 `pending`，`expires_at = created_at + pending_hold_minutes`。

## 2. API 契约

### 2.1 公开创建（guest / 自助）

`POST /api/store/public/appointments` — 无需登录，按 IP + `store_id` 限流。

Headers：`Idempotency-Key` 可选（§7）。

```json
// request
{
  "store_id": "uuid",
  "items": [
    { "service_id": "uuid", "option_id": "uuid | null" }
  ],
  "staff_id": "uuid | null",
  "start": "2026-10-05T09:00:00",
  "contact": { "name": "李女士", "phone": "416-123-4567", "email": "a@b.com | null" },
  "notes": "string | null"
}
```

- `items` ≥ 1；`price_type='from'` 的服务必须带 `option_id`（沿用 slot engine 的 `OPTION_REQUIRED`）。
- `staff_id: null` = "任意员工"（§4）。
- `start` 是门店本地时间，必须精确命中一个当前有效的 slot 开始点（§3 重校验）。

```json
// response 201
{
  "id": "uuid",
  "reference_code": "F7AE5724",
  "status": "confirmed | pending",
  "store_id": "uuid",
  "staff_id": "uuid",
  "starts_at": "2026-10-05T09:00:00",
  "ends_at": "2026-10-05T10:00:00",
  "items": [
    { "service_id": "uuid", "service_name": "深层清洁 (snapshot)",
      "option_id": null, "option_name": null,
      "duration_minutes": 60, "price_cents": 8800,
      "starts_at": "2026-10-05T09:00:00", "ends_at": "2026-10-05T10:00:00" }
  ],
  "total_price_cents": 8800,
  "expires_at": "2026-10-05T09:15:00 | null"
}
```

- `expires_at` 仅 `pending` 时有值。
- `reference_code`：8 位大写字母数字，全局唯一，给客户看的预约号（对标 Fresha 的 `#F7AE5724`）。

### 2.2 员工手工创建（电话/walk-in/后台录入）

`POST /api/store/appointments` — `StoreSession`，`storeId ∈ caller.AuthorizedStoreIds`。

Body 同 2.1，另加：
- `is_test: bool`（默认 false）——测试预约的 checkbox。
- `contact` 可带 `customer_id`（店里客户档案解析出的 `customer.customers.id`；解析规则归未来的客户档案文档，本篇只收这个 id）。

差异行为：
- 允许 `is_test=true`（公开接口永远 false，传了也忽略）。
- **跳过 `min_lead_minutes`**：员工站在店里给客人当场约，不应被"提前量"卡；营业时间/排班/double-booking 校验一律保留。
- 其余与 2.1 同一事务（§8），不另写第二条路径——**任何绕过 quota/double-booking 的手工路径都是 bug**。

### 2.3 确认 / 取消 / 改期

| 方法与路径 | 谁可调 | 说明 |
|---|---|---|

| `POST /api/store/appointments/{id}/cancel` | 同上，或预约的客户本人（客户侧"My Bookings"文档定） | §10 规则 |

## 3. Slot 二次校验（创建时必做）

**不信任**创建前查到的 slots 结果。对请求的 `(staff_id, start)` 跑一次 slot engine 的单人单日计算（§4 Step 1–7，指定员工模式），`start` 必须落在算出的可行开始点集合里，否则 `409 SLOT_TAKEN`。

- 这次计算必须包含 `pending` 未过期的预约占用（slot engine v1 只减 `confirmed`——**本篇决议后 engine 要同步改**：Step 5 改为减去 `status IN ('pending','confirmed')`，`pending` 且 `expires_at < now()` 的不减）。
- `is_test` 的预约照占（真实员工时间），与 engine 现有语义一致。
- **容量二次校验（2026-09-30，§18）**：同一次重校验里，对请求的 `(store_id, start)` 额外算一遍店级容量——该 `start` 的候选块 `[s - Bb, s + D + Ba]` 若落在当时的"满区间"里，`409 CAPACITY_FULL`（不是 `SLOT_TAKEN`，错误码要分清楚：员工忙 vs 店里满，文案不一样）。`booking_settings.capacity IS NULL` 的店跳过此项，行为不变。
- 校验通过不等于拥有——最终由 §5 的 exclusion constraint 兜底（staff 维度）+ §18 的 store 级 advisory lock（容量维度）兜底，冲突时报 `409 SLOT_TAKEN` 或 `409 CAPACITY_FULL`，客户端引导重选。

## 4. "任意员工"指派

`staff_id: null` 时，服务端取**本次重校验**算出的该 `start` 的 `staff_ids` 列表（slot engine 已按员工 sort_order/创建时间排序），取第一个，写入 `appointments.staff_id`。响应里返回实际指派的人。

- 确定性：同样的输入永远指派同一个人（v1 可预测、可复现、可测试）。
- 并发下两个"任意"请求可能算出同一个人——由 exclusion constraint 串行化，输的那个拿 `409 SLOT_TAKEN`（§9 case 2）。

## 5. 防 double-booking：exclusion constraint

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- 只有 pending/confirmed 才产生占用区间；终态一律 NULL（exclusion 跳过 NULL 行）
ALTER TABLE store.appointments
  ADD COLUMN occupied_range TSTZRANGE
    GENERATED ALWAYS AS (
      CASE WHEN status IN ('pending', 'confirmed')
           THEN tstzrange(starts_at, ends_at)
      END
    ) STORED;

ALTER TABLE store.appointments
  ADD CONSTRAINT no_double_booking
  EXCLUDE USING gist (staff_id WITH =, occupied_range WITH &&);
```

- 同一人、占用区间重叠的两行**不可能同时存在**——这是整个系统"绝不 double-book"的最后防线，不依赖任何应用层锁。
- `is_test` 同样受约束（它占真实时间）。
- `btree_gist` 是因为 `staff_id` 是 UUID（`=` 需要 gist 支持）；`tstzrange` 的 `&&` 原生支持。
- 应用层**不**加 advisory lock：锁在进程崩溃/多实例下会漏，约束不会。§3 的重校验是用来给用户友好错误的（精确的 `SLOT_TAKEN`），约束是用来保证正确性的。

**店级容量（§18）为什么是例外，精确的理由（2026-09-30）**：真正的边界不是"维度不同就换原则"，而是**exclusion constraint 只能表达"任意两行不能重叠"（pairwise），表达不了"同时最多 N 行"（counting）**——这是硬技术限制，不是选型偏好。以后再遇到类似需求，判断标准是看不变量的形状（pairwise 用约束，counting 没有约束等价物），不是看"这是 staff 维度还是 store 维度"。

同时要澄清：上面"锁在进程崩溃/多实例下会漏"批评的是**应用进程内存里的锁**（比如 C# 的 `lock` 语句，或没做好 fencing 的 Redis 锁）——这类锁的状态活在某一个进程里，那个进程一死或者一多实例，锁的语义就碎了。`pg_advisory_xact_lock`（§18 用的）是**Postgres 服务端、绑定事务生命周期**的锁：commit/rollback/断连都会自动释放，而且锁表本身是数据库共享的，不是任何一个 app 实例的内存——两个不同的 app 实例对同一个 key 调用，照样被 Postgres 正确串行化。换句话说，它不是本节批评的那种锁，两者不矛盾。

## 6. 多服务排期

请求 `items` 按数组顺序背靠背排：

```
cursor = start
for i, item in enumerate(items):
    D_i  = option?.duration_minutes ?? service.duration_minutes
    Bb_i = service.buffer_before_minutes ?? store.buffer_before_minutes
    Ba_i = service.buffer_after_minutes  ?? store.buffer_after_minutes
    item.starts_at = cursor
    item.ends_at   = cursor + D_i
    cursor = item.ends_at + (max(Ba_i, Bb_{i+1}) if i+1 exists)
header.starts_at = start
header.ends_at   = items.last.ends_at
header.buffer_before_minutes = Bb_0
header.buffer_after_minutes  = Ba_last
```

- 每个 item 的价格快照：`price_cents`（`free`=0；`fixed`=服务价；`from`=所选 option 价）、`service_name`、`option_name`、`duration_minutes`。
- 总时长（含内部 buffer 间隙）必须整体落在重校验的可行区间里——实现上即 `header` 的 `[starts_at - Bb_0, ends_at + Ba_last]` 要能被该员工当天的可用时间容纳。
- 单人单块：多服务**不**拆人（基线已定）。

## 7. 幂等

- 公开创建支持 `Idempotency-Key` header（员工端**要求**传，公开端可选）。
- 语义：`(store_id, key)` 24 小时内，同 key + 同请求体哈希 → 直接返回上次的 201 响应（**不**建第二行）；同 key + 不同请求体 → `422 IDEMPOTENCY_KEY_REUSED`。

```sql
CREATE TABLE store.idempotency_keys (
  store_id      UUID NOT NULL REFERENCES store.stores(id),
  key           TEXT NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  request_hash  TEXT NOT NULL,
  response_status INT NOT NULL,
  response_body JSONB NOT NULL,
  PRIMARY KEY (store_id, key)
);
-- 定时清理 created_at < now() - interval '24 hours'
```

## 8. 事务边界（单个 DB 事务）

```
BEGIN
  0. 取 store 级 advisory 锁（§18）：
     SELECT pg_advisory_xact_lock(hashtext('groway:store_appt:' || store_id::text));
     （仅当该店 capacity IS NOT NULL 才有意义去"抢"，但锁本身可以无条件取——
     对 capacity=NULL 的店，锁开销可忽略，不必加分支。）
  1. 解析并校验输入：store/service/option/staff 存在性（跨店 → 404），
     items 非空，from 必带 option，start 格式合法。
  2. 定 staff：staff_id 有值用它；null 则 §4 指派。
  3. 算时长/buffer/排期（§6）→ starts_at/ends_at。
  4. Slot 重校验（§3，含容量二次校验）：不通过 → 409 SLOT_TAKEN 或 409 CAPACITY_FULL
     （回滚，无副作用）。
  5. Quota：is_test=false → BillingQuotaService.TryConsumeAsync(storeId)，
     同一事务内；失败 → 409 QUOTA_EXHAUSTED（回滚，计数器增量随事务回滚）。
     is_test=true → 跳过。
  6. 生成 reference_code（8 位，唯一冲突则重试）。
  7. INSERT appointments（status 按 auto_confirm/payment_required 定，
     pending 则 expires_at = now() + pending_hold_minutes；
     occupies_capacity = 各 item 对应服务 occupies_capacity 的 OR，§18）
     + INSERT appointment_items（快照）
     + UPSERT idempotency_keys（若传了 key）
     + INSERT store.outbox（§11 事件）
COMMIT
-- exclusion violation → 409 SLOT_TAKEN；unique violation on reference_code → 重试生成
-- advisory 锁随 COMMIT/ROLLBACK 自动释放，无需显式 unlock
```

- 顺序要点：**先取锁、先重校验、后吃 quota**——锁要在第 0 步就拿到，保证第 4 步的容量重校验和第 7 步的 INSERT 对同一个 store 是串行的；slot/容量都没有就别浪费 quota 计数。
- Quota 计数点：行 INSERT 时（既定规则）。`pending` 也计数——15 分钟的占位是真实消耗的 slot；过期不退款（与 cancelled 照计 quota 同一逻辑）。
- 失败一律回滚：quota 增量、预约行、幂等记录、outbox 要么全有要么全无；advisory 锁同样回滚释放。

## 9. 并发测试用例（实现后必跑）

1. 同一员工+同一 `start`，两个请求同毫秒到达 → 一个 201，一个 `409 SLOT_TAKEN`；DB 里只有一行。
2. `staff_id=null`，某 `start` 只有一个员工有空 → 两个并发请求，一个 201（指派给该员工），一个 `409 SLOT_TAKEN`。
3. `pending` 在 TTL 边界：`expires_at` 前 1 秒 confirm 成功；sweeper 在 TTL 后 1 秒跑 → `expired`，且 `occupied_range` 变 NULL 后该 slot 可被重新预约。
4. 同一预约两个并发改期 → 一个成功，一个 `409 SLOT_TAKEN`（或乐观锁冲突，见 §10）。
5. 免费版 quota 在 99/100 边界：两个并发创建 → 恰好一个 `409 QUOTA_EXHAUSTED`，`billing_appointment_usage` 停在 100。
6. 同 `Idempotency-Key` 发两次 → 同一个 `reference_code`，DB 只有一行，第二次返回第一次的响应体。
7. 改期并发 + 新建并发抢同一目标 slot → 只有一个赢。

**容量（§18）用例，2026-09-30 追加：**

8. `capacity=2`，同一时段已有 2 个 `confirmed` 预约 → 第三个重叠时段的创建返回 `409 CAPACITY_FULL`，DB 无新增行。
9. `capacity=1`，员工 A、B 当天都空闲：先给 A 约 09:00 成功 → 再给 B 约 09:00（B 完全空闲）→ 必须 `409 CAPACITY_FULL`（证明容量维度独立于 staff 维度生效）。
10. `capacity=1`，09:00–10:00 已满 → 查 slots：09:00 的 slot 不出现，但 10:00 的 slot 正常出现。
11. 并发：`capacity=1`，两个请求同毫秒抢同一时段不同员工 → 一个 201，一个 `409 CAPACITY_FULL`；DB 里只有一行（advisory 锁生效）。
12. `occupies_capacity=false` 的服务：在容量已满的时段仍可预约成功，且不计入并发数。
13. `pending` 过期后（sweeper 跑过或 `expires_at < now()`）：容量释放，该时段可重新预约。
14. `capacity=NULL` 的店：Step 5b 跳过，行为与改前完全一致（回归测试）。
15. 改期：把预约改到容量已满的时段 → `409 CAPACITY_FULL`，原预约不动。
16. 取消已满时段中的一个预约 → 该时段 slots 重新出现。

## 10. 取消与改期规则

**取消**（`→ cancelled`）：
- 客户自助取消：`starts_at - now() < cancel_threshold_hours` → `409 CANCEL_TOO_LATE`（`0` = 随时可退）。被拒时提示打电话到店里。
- 员工（`AuthorizedStoreIds` 内）：随时可取消，不受 threshold 约束。
- `cancelled` 不退 quota（既定规则），`occupied_range` 自动变 NULL 释放 slot。

**改期**（原地 `UPDATE starts_at/ends_at[/staff_id]`）：
- 对新 `(staff, start)` 跑完整 §3 重校验（含容量）+ §6 重排期；exclusion constraint 防并发冲突（staff 维度）。
- **同样先取 §18 的 store 级 advisory 锁**，再做容量重校验——改期和新建抢同一目标时段时，锁把两者串行化，只有一个赢（§9 case 7 的精神，容量维度同理）。
- 同一 id，不新增行 → **不重复计 quota**（§0 裁决 6 的理由）。
- 客户自助改期同样受 `cancel_threshold_hours` 约束（逻辑上是"退了重订"）；员工随时可改。
- v1 用 exclusion constraint 做并发保护即可；`updated_at` 变化可用于客户端"是否被别人动过"的弱提示，强乐观锁（version 列）v2 再加。

**终态流转**：
- `no_show`：仅员工标记（back-office 日历文档定 UI）。
- `completed`：sweeper 周期性 `UPDATE ... SET status='completed' WHERE status='confirmed' AND ends_at < now()`，幂等；员工也可提前手动标。
- `expired`：sweeper `UPDATE ... SET status='expired' WHERE status='pending' AND expires_at < now()`，幂等。

## 11. 事件（outbox）

同一事务内写 `store.outbox`，relay worker 投递给通知/提醒管线（确认短信、reminder 的具体模板与时机是下一篇 `customer-booking-confirmation-reminders.md` 的事，本篇只保证事件不丢）：

| event_type | 何时 |
|---|---|
| `appointment.created` | 创建提交（含 status） |
| `appointment.confirmed` | `pending → confirmed` |
| `appointment.cancelled` | 任何 `→ cancelled`（带 `cancelled_by: customer/staff`） |
| `appointment.rescheduled` | 改期成功（带 old/new starts_at） |
| `appointment.expired` | `pending → expired` |

```sql
CREATE TABLE store.outbox (
  id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  aggregate_type TEXT NOT NULL DEFAULT 'appointment',
  aggregate_id   UUID NOT NULL,
  event_type     TEXT NOT NULL,
  payload        JSONB NOT NULL,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  published_at   TIMESTAMPTZ
);
```

## 12. Guest 与登录客户

- v1 公开端**不强制登录**：`contact.name` + `contact.phone` 必填，`customer_id` 留 NULL，`guest_*` 列存快照。
- 员工端可传 `customer_id`（店里客户档案解出的 `customer.customers.id`；档案本身的建档/查重规则归未来的客户档案文档）。
- "My Bookings"（客户查自己的预约、取消、改期）是下一篇客户侧文档的事——本篇只保证 `customer_id` 有地方存、`reference_code` 可用于凭码查询。

## 13. `payment_required=true` 的挂钩（v1 最小）

- 创建走 `pending`，`expires_at` 同 pending TTL。
- 预约行预留 `payment_intent_id TEXT`（provider 回来填）。
- 支付成功回调 → `pending → confirmed`（走 `appointment.confirmed` 事件）。
- provider 选型、deposit 金额规则、预授权/捕获/退款——**另起文档**，本篇不展开。`payment_required=false` 的店完全不受影响。

## 18. 店级并发容量（床位），2026-09-30 追加

定位：店级容量是 staff 维度之外**新增的一个维度**（同一时段店内同时进行的、占床位的预约数不得超过该数），不是对 §1–§17 任何既有规则的修改。Schema（`booking_settings.capacity`、`services.occupies_capacity`、`appointments.occupies_capacity`）已经合入 `store-onboarding-v1-design.md`，本节只定本篇范围内的事：二次校验、并发串行化、header 快照写入、测试用例、未决事项。

### 18.1 "占床位"的判定（与 slot engine Step 5b 共用口径）

一条 `store.appointments` 在以下全部成立时计入并发数：
- `occupies_capacity = true`（头快照）；
- `status IN ('pending', 'confirmed')`（与 §17 的 engine 同步决议同一口径）；
- `status = 'pending'` 时：`expires_at IS NULL OR expires_at > now()`（过期 pending 视为已释放）；
- 占用区间：`[starts_at - buffer_before_minutes, ends_at + buffer_after_minutes]`——用头上的 buffer 快照，与 §5/§6 的员工占用区间完全一致。

`is_test` 预约照占（占的是真实床位），与 §2.2 末句"任何绕过校验的手工路径都是 bug"同一原则。

### 18.2 二次校验与并发串行化

见 §3（二次校验挂进去了）、§5 末尾（为什么 exclusion constraint 表达不了这个约束、为什么 `pg_advisory_xact_lock` 不违反 §5 的原则）、§8 第 0/4/7 步（锁的位置、容量校验的位置、header 快照的写入点）。

`pg_advisory_xact_lock(hashtext('groway:store_appt:' || store_id::text))` 把同一 store 的创建/改期请求串行化，不同 store 互不影响；随事务提交/回滚自动释放。性能：单店低并发场景，锁持有时间 = 一次事务（毫秒级），可接受。

### 18.3 Nightly 审计（2026-09-30，Q4 裁决）

v1 不做"容量被突破"的实时拦截之外的第二道防线——advisory 锁已经是正确性保证，但正确性**完全依赖"以后每条创建/改期路径都记得先取锁"这条纪律**，不像 staff 维度有 exclusion constraint 这种数据级兜底。为防未来某个绕过本篇事务的路径（批量导入工具、后台脚本直接 INSERT）悄悄突破容量却无人知晓，加一道**事后审计**，不是实时拦截：

- 每晚一个 Kubernetes CronJob（沿用 billing reminders / notifications 的 CronJob 模式），扫过去 7 天：对每个 `capacity IS NOT NULL` 的店、每一天，按 §18.1 的判定重新 sweep 一遍实际并发数，凡是曾经（或现在）出现并发数 > capacity 的时间段，写入下表并通知该店的 `chain_admin`（复用 `groway-store-notifications-workflow.md` 的消息板机制，`message_type='system'`）。
- 悄悄突破变成第二天早上就知道——试点阶段够用，不是实时correctness 机制的替代品。

```sql
CREATE TABLE store.capacity_breaches (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  store_id        UUID NOT NULL REFERENCES store.stores(id),
  day             DATE NOT NULL,
  window_start    TIMESTAMPTZ NOT NULL,
  window_end      TIMESTAMPTZ NOT NULL,
  capacity        INT NOT NULL,          -- 当时配置的容量，留痕（以后改了容量，历史审计记录不随之改写）
  concurrent_count INT NOT NULL,         -- 实际检测到的并发数
  detected_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  notified_at     TIMESTAMPTZ
);
CREATE INDEX idx_capacity_breaches_store_day ON store.capacity_breaches(store_id, day);
```

- 幂等：同一 `(store_id, window_start, window_end)` 重复检测到 → `ON CONFLICT DO NOTHING`（不重复通知）。
- 这张表只增不改——即使后来发现是误报（比如数据修复后），也不删行，保留审计原貌；需要的话另加 `resolved_at` 之类的字段，v1 不做。

### 18.4 范围之外（明确推迟）

- 逐个床位指派（"1 号床、2 号床"归谁）——员工在店里看得见，不需要系统分配。
- 不同房间类型/设备（面部房 vs 头疗区，蒸汽机等）——等医美店再说。
- 按时段变化的容量、容量预占、waitlist 联动。
- `capacity` 是否允许设为 0（= 暂停接单）——按 `CHECK >= 1`，暂停接单走现有的"关店/关服务"路径，不复用本字段。
- 容量与 quota 的关系：quota 计"预约数"，容量限"并发数"，两个维度正交，互不影响，本节不再重复论证。
