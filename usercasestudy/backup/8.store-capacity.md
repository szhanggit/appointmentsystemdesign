## 0. 一句话

v1 在 staff 维度之外加一个店级并发容量（对头疗店就是"床位数"）：同一时段店内同时进行的、占床位的预约数不得超过该数。客户侧无感（不选床、不看到床），系统自动拦截超卖。

**为什么要做**：迁移门槛是"证明没有 double-booking"，而床才是客户实际体验到的被 double-book 的东西。店里床比员工少时（3 员工 2 张床，周六爆满），光靠 staff 维度算 slot 会超卖——两个客户同时约进来，员工都空闲，但床不够。

## 1. 范围

**做：**
- `booking_settings` 新增店级容量字段（NULL = 未配置 = 不限）。
- `services` 新增 `occupies_capacity` 开关（默认 true；电话咨询这类不占床的服务可设 false）。
- slot engine：容量满的时段不出 slot（Step 5b）。
- 创建事务：容量二次校验 + 并发串行化。
- 改期：新时间同样受容量校验。
- 新错误码 `CAPACITY_FULL`（409）。
- Nightly 审计（事后兜底，§5 见下）。

**不做（v1 明确推迟）：**
- 逐个床位指派（"1 号床、2 号床"归谁）——员工在店里看得见，不需要系统分配。
- 不同房间类型（面部房 vs 头疗区）、设备（蒸汽机）——等医美店再说。
- 按时段变化的容量、容量预占、waitlist 联动。

## 2. Schema（已合入 `store-onboarding-v1-design.md`，建表语句直接带，不走 ALTER）

```sql
-- booking_settings：NULL = 店主未配置 = 不限（向后兼容，不设假默认值）
capacity INT CHECK (capacity IS NULL OR capacity >= 1)

-- services：默认占床位
occupies_capacity BOOLEAN NOT NULL DEFAULT true

-- appointments：预约头快照，创建时按各 item 服务的 occupies_capacity 取 OR
occupies_capacity BOOLEAN NOT NULL DEFAULT true
```

`is_test` 预约照占（占的是真实床位），与现有"测试预约占员工时间"语义一致。服务改了开关不追溯历史预约——与价格/时长快照同一逻辑。

## 3. "占床位"的判定（slot engine 与创建事务共用，`1.create-appointment-transaction.md` §18.1 定稿）

一条 `store.appointments` 在以下全部成立时计入并发数：
1. `occupies_capacity = true`（头快照）；
2. `status IN ('pending', 'confirmed')`；
3. `status = 'pending'` 时：`expires_at IS NULL OR expires_at > now()`（过期 pending 视为已释放）；
4. 占用区间：`[starts_at - buffer_before_minutes, ends_at + buffer_after_minutes]`——用头上的 buffer 快照，与 slot engine 的员工占用区间完全一致。

## 4. Slot engine（已落地：`availability-slot-engine.md` §4 Step 5b）

现有 Step 1–8（按员工算 slot）不变，在 Step 8 合并之前插入店级容量过滤：仅当 `capacity IS NOT NULL` 才生效；store 级 sweep 算出"满区间"；任何候选 `start` 的块与满区间相交就整体丢弃（"任意员工"模式丢的是整个 `start` key，不是某个 `staff_id`——容量满了换谁都没用）。性能：O(n log n)，v1 实时计算不缓存。

## 5. Create transaction（已落地：`1.create-appointment-transaction.md` §3/§5/§8/§18.2）

- §3 的 slot 重校验加入容量检查，落在 → `409 CAPACITY_FULL`。
- 并发串行化：**店级 `pg_advisory_xact_lock`**，事务第 0 步取，随 commit/rollback 自动释放。
  - **这不是"按维度换原则"，是硬技术边界**：exclusion constraint 只能表达 pairwise 不重叠，表达不了 counting（同时最多 N 行）——这是 staff 维度继续用约束、容量维度必须换机制的真正原因。
  - `pg_advisory_xact_lock` 不是 §5 原本批评的那种锁：那条批评针对的是应用进程内存里的锁（C# `lock`、没做 fencing 的 Redis 锁），进程一死/一多实例就碎。`pg_advisory_xact_lock` 是 Postgres 服务端、绑定事务生命周期的锁，多实例下照样被数据库正确串行化，进程崩了锁不会成孤儿。两者不是一回事，没有推翻 §5 的原则。
- §8 事务步骤：0. 取 store advisory 锁 → 1. 校验输入 → 2. 定 staff → 3. 排期 → 4. slot 重校验 + 容量校验 → 5. quota → 6. 生成 reference_code → 7. INSERT（含 `occupies_capacity` 快照）→ COMMIT。
- 改期同样先取锁、同样重校验容量（`1.create-appointment-transaction.md` §10）。

## 6. 风险与兜底：Nightly 审计（Q4 裁决，已落地 §18.3）

容量正确性**完全依赖"每条创建/改期路径都记得先取锁"这条纪律**，不像 staff 维度有 exclusion constraint 数据级兜底——以后若有代码绕过本事务（批量导入、后台脚本直连 INSERT），容量会悄悄被突破且无人知晓。

v1 接受这个风险，但加一道**事后**保险：每夜 CronJob 扫过去 7 天，重新 sweep 实际并发，超了就写 `store.capacity_breaches` 表并通知 `chain_admin`（复用消息板机制）。悄悄突破变成第二天早上就知道——不是实时 correctness 机制的替代品，试点阶段够用。

## 7. API 与错误码（已落地）

- `GET /api/store/public/slots`：响应结构不变，容量满的时段直接不出现。
- `POST /api/store/public/appointments` / `POST /api/store/appointments`：容量满 → `409 CAPACITY_FULL`，文案"该时段已约满，请选择其他时间"。

## 8. Onboarding / 后台设置

- UI 层面必填（建店向导必须二选一：填数字或亲手选"不限"），**后端不强制**——`capacity` 保持 NULL-able，不改建店 API 契约，老店/未配置的店零风险迁移。
- 文案面向店主（business 语言）："同时最多接待几位客人？"，不出现 resource/capacity 术语。
- 服务设置页每个服务一个开关："该服务需要占用一个接待位"，默认开。

## 9. 验收测试用例（已追加到 `1.create-appointment-transaction.md` §9，案例 8–16）

1. `capacity=2`，已有 2 个 `confirmed` → 第三个重叠创建 `409 CAPACITY_FULL`，DB 无新增行。
2. `capacity=1`，A、B 都空闲：A 约 09:00 成功 → B 约同一 09:00 → `409 CAPACITY_FULL`（证明容量独立于 staff 维度）。
3. `capacity=1`，09:00–10:00 已满 → 查 slots：09:00 不出现，10:00 正常。
4. 并发：`capacity=1`，两个请求同毫秒抢同一时段不同员工 → 一个 201，一个 `409 CAPACITY_FULL`；DB 只有一行。
5. `occupies_capacity=false` 的服务：容量已满时段仍可约，不计入并发。
6. `pending` 过期后：容量释放，可重新预约。
7. `capacity=NULL` 的店：Step 5b 跳过，行为与改前完全一致（回归）。
8. 改期到容量已满的时段 → `409 CAPACITY_FULL`，原预约不动。
9. 取消已满时段中的一单 → 该时段 slots 重新出现。

## 11. 本需求未决 / 明确不做

- 床位逐个指派、房间类型、设备——v1 不做（§1）。
- `capacity` 是否允许设为 0（= 暂停接单）？v1 按 `CHECK >= 1`，暂停接单走现有的"关店/关服务"路径，不复用本字段。
- 容量与 quota 的关系：quota 计"预约数"，容量限"并发数"，两个维度正交，互不影响。
