# Public Booking End-to-End（2026-09-29 v1 草案）

本地 spec，供 Claude Code 实现。**只存本地，不上 GitHub。**

定位：客户自助预约的完整链路——从打开预约页到看到确认页。把前面四篇串起来：slot engine（查时间）→ transaction（下单）→ reminders（短信）。本篇不定新逻辑，只定**步骤顺序、每步调什么接口、失败时 UI 怎么反应**。

基线事实：
- 步骤顺序沿用 v1 scope 已定的：service → staff → time → client info → confirm（GOAL.md）。
- 公开接口无需登录，按 IP + `store_id` 限流。
- 价格：`from` 显示价实时取 `min(options)`（service-catalog-design.md）。

## 0. 本篇的裁决（先看结论）

1. **v1 公开流程一次只约一个服务（+option）**。理由：多服务连约的 slot 计算 engine 还没设计（engine §8 item 3）；先让单服务链路可上线，多服务走员工手工单（transaction 已支持）。v2 解锁条件：engine 支持多服务合并 slot。
2. **确认页给 .ics 日历文件下载**。理由：实现成本极小（前端拼字符串），防忘效果好。
3. **下单按钮防连点 + `Idempotency-Key`** 双保险。理由：移动端弱网下用户会狂点确认。
4. **409 SLOT_TAKEN 不弹错误页**，直接当场重查当天 slots 并高亮可选项。理由：被抢时间是正常业务，流程不该断。

## 1. 流程总览

```
/book/{store_id}
  Step 1 服务 → Step 2 员工 → Step 3 日期时间 → Step 4 联系方式 → Step 5 核对 → 确认页
```

- 顶部步骤条，可回退（回退保留已选）。
- 每步的数据只依赖前序选择；`store_id` 全程带在 URL 里。

## 2. 分步规格

### Step 1 — 选服务

- 调：`GET /api/store/services?store_id=`（catalog 有列表接口；只有 `status='active'`、未删、可在线约的）。
- 分组按 category 显示；`from` 服务显示"¥起"（`min(options)` 实时算）；`free` 显示"免费"。
- `from` 服务下一步先选 option（选项列表同接口返回），再进 Step 2。

### Step 2 — 选员工

- 选项："任意可用"（默认）+ 可约该服务的员工列表（头像/名字）。
- 数据来源：`GET /api/store/staff?store_id=&service_id=`（有 staff 列表接口；无则用 slots 的聚合——v1 要求有，deferred 里记一笔也行，见 §8）。
- 选"任意" → `staff_id: null` 进下一步。

### Step 3 — 选日期时间

- 日期选择器：`today(store_tz) ~ today + advance_booking_days`；过去置灰。
- 选日期后调：`GET /api/store/public/slots?store_id=&service_id=&option_id=&date=&staff_id=`。
- 时间按 `slot_granularity_minutes` 列表展示；"任意员工"模式每个时间点可展开看是哪几位（v1 只显示时间，员工悬念留到确认页揭晓——简单；想看的点 Step 2 指定人）。
- 当天无空位：文案"这一天约满了"，给"后一天"快捷跳转（调下一天的 slots，有就跳）。

### Step 4 — 联系方式

- 姓名 + 手机号必填；邮箱选填（有邮箱才发确认邮件）。
- 手机号格式校验（加拿大 10 位，v1 只做格式不做 OTP——OTP 是防刷号的，限流已 cover，v1 不上）。
- 同意条款 checkbox 一句话："预约确认与提醒短信将发送到此号码"。

### Step 5 — 核对

- 显示：店名、服务（+option）、员工（"任意"则写"到店安排"）、日期时间、价格、姓名电话。
- 确认按钮："确认预约"。

### 确认页

- 大字 `reference_code` + 预约详情 + "确认短信已发送到 xxx"。
- 按钮：[下载日历 (.ics)] [再约一个]。
- 文案："改期/取消请致电 {store_phone}"（自助改期是 My Bookings 文档的事，v1 没有链接）。
- `pending` 状态（`auto_confirm=false` 的店）：页面显示"已收到，等店家确认"，短信模板也是 pending 版（reminders doc §5）。

## 3. 下单请求（Step 5 → 确认页）

```
POST /api/store/public/appointments
Idempotency-Key: <uuid v4, 进入 Step 5 时生成，整个 Step 5 会话内不变>
{ store_id, items: [{service_id, option_id}], staff_id, start, contact: {name, phone, email}, notes: null }
```

- 按钮点击后立即 disable，响应回来前不接受第二次点击。
- 成功 201 → 确认页（`reference_code`、`status`）。
- `409 SLOT_TAKEN` → **不报错页**：toast"这个时间刚被约走"，自动重调当日 slots，原 Step 3 状态恢复，时间列表刷新。
- `409 QUOTA_EXHAUSTED` → 整页提示（billing §4.3 文案）："本店本月预约已满，请直接致电 {store_phone}"。
- `409 STAFF_NOT_AVAILABLE` / `400` 系列 → 回到对应步骤并标红。
- 网络失败/超时：**不自动重试下单**——用户点"重试"按钮，用**同一个** `Idempotency-Key` 重发（服务端去重保证只建一单；§9 case 1 覆盖）。

## 4. 入口

- 预约页 URL：`/book/{store_id}`。店里摆台卡 + QR 码 → 同一 URL。
- `store_id` 不存在/未 active → 404 页"这家店暂未开通在线预约"（不泄露存在性细节）。
- 分享：确认页 URL 不带敏感信息（`reference_code` 只在页面内显示一次，不进 URL）。

## 5. 响应式与体验要点（v1 最小）

- 移动优先：单列步骤；时间列表大按钮（≥44px 触摸区）。
- 全程中文/英文跟随 `notification_lang`？——v1：页面语言跟随浏览器，短信按 §5 规则。页面 i18n 框架要有，文案先上 en + zh。
- 加载态：slots 查询 300ms 内出骨架屏，超时则"重试"按钮。

## 7. E2E 测试清单

1. 完整走一单：选服务→员工→时间→填信息→确认→201→确认页显示 `reference_code`→1 分钟内收到短信。
2. 两个手机同时抢同一 slot → 一个成功进确认页，一个 toast + 列表刷新，无重复建单。
3. 弱网下连点 3 次确认 → 只建一单（同 `Idempotency-Key`）。
4. 下单超时后点"重试" → 同一 `reference_code`，DB 一行。
5. 免费版 quota 满 → 看到致电提示页，无残留预约。
6. `auto_confirm=false` 的店 → 确认页显示"等店家确认"，收到 pending 短信。
7. 回退：Step 5 回到 Step 3 换时间 → 下单用的是新时间。
8. 过期日期/非法 `store_id` → 正确的 400/404 页。

## 8. 推迟

1. `GET /api/store/staff`（按服务过滤的可约员工列表）——如无，先用 slots 按天聚合凑合，v2 补正式接口。
2. 多服务连约的公开流程（等 engine 支持多服务合并 slot）。
3. 会员登录 / My Bookings（自助查单、改期、取消）。
4. .ics 之外的"添加到 Google/Apple 日历"深链。
5. 小费/定金（`payment_required` 另起文档）。
