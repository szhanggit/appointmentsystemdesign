# Customer Booking Confirmation & Reminders（2026-09-29 v1 草案）

本地 spec，供 Claude Code 实现。**只存本地，不上 GitHub。**

定位：面向**客户**的通知管线。消费 `create-appointment-transaction.md` §11 的 outbox 事件（`appointment.created/confirmed/cancelled/rescheduled/expired`）。`chain_admin` 的消息板（blocked-booking digest 等）是 `groway-store-notifications-workflow.md` 的事，本篇不碰。

基线事实：
- 渠道：短信走 Twilio（定价文档已确认 Twilio 为短信渠道），邮件走 SES（notifications 文档的 digest 已用 SES）。
- 第三方直接成本由合伙人承担（既定）；本篇只记账，不做向门店转嫁的逻辑。
- 时间一律门店时区；`reference_code` 是给客户看的预约号。

## 0. 本篇的裁决（先看结论）

1. **两次提醒：T-24h 和 T-2h**。理由：24h 够改期，2h 防当天忘；第三次就是骚扰。
2. **确认走短信 + 邮件，提醒只走短信**。理由：短信打开率最高；确认需要留档（邮件），提醒要的是"被看到"。
3. **夜间 21:00–08:00（门店时区）不发短信**，提醒顺延到 08:00，**不跳过**。理由：凌晨 3 点的提醒不如不发；但跳过等于没提醒。用户刚下单触发的确认短信不受此限（是他自己要的）。
4. **定时器 = 每 5 分钟扫一次的 poller**，不是分布式定时消息。理由：v1 没有定时消息基础设施；poller + 已发送标记天然幂等，重启不丢。
5. **模板双语（en/zh）**，按客户语言偏好，无则按店默认。理由：Richmond Hill spa 客群。
6. **费用逐条记账**，合伙人付（既定）。v1 不做向门店分摊。
7. **短信 STOP 退订**：退订后短信停发，自动降级走邮件；都没得走就只记日志。理由：CASL + 基本体面。

## 1. 事件 → 通知映射

| outbox 事件 | 通知 | 渠道 | 时机 |
|---|---|---|---|
| `appointment.created`（status=confirmed） | 预约确认 | SMS + Email | 立即 |
| `appointment.created`（status=pending） | 已收到，等确认 | SMS（+Email 如有） | 立即 |
| `appointment.confirmed` | 预约确认 | SMS + Email | 立即 |
| `appointment.cancelled` | 取消确认 | SMS + Email | 立即 |
| `appointment.rescheduled` | 改期确认（新时间） | SMS + Email | 立即 |
| `appointment.expired` | 占位过期 | SMS | 立即 |
| （调度器） | 24h 提醒 | SMS | `starts_at - 24h` |
| （调度器） | 2h 提醒 | SMS | `starts_at - 2h` |

- 事件驱动的通知（确认/取消/改期/过期）由 outbox relay 触发，**发送前重查预约状态**：比如 relay 延迟，`created(confirmed)` 的消息发出前预约已被取消 → 不发确认，只发取消（查最新状态，按最新状态选模板）。
- 员工手工建的预约（电话/walk-in）同样发送——短信里有 `reference_code`，是纸质凭证，防"我不知道"纠纷。

## 2. 提醒调度器

`store` schema 内一个 Kubernetes CronJob（沿用 billing reminders 的 CronJob 模式），每 5 分钟跑一次：

```sql
-- 24h 提醒到期：还没发过、预约仍是 confirmed、starts_at 在未来 24h 内
SELECT id, store_id FROM store.appointments
WHERE status = 'confirmed'
  AND reminder_24h_sent_at IS NULL
  AND starts_at > now()
  AND starts_at <= now() + interval '24 hours';
-- 2h 同理（interval '2 hours'，列 reminder_2h_sent_at）
```

- 扫到后先查**夜间窗口**（§3），要顺延的这次不标已发送，下一次 poll 继续。
- 发送成功才写 `reminder_*_sent_at`；发送失败不写，下一次 poll 重试（§6）。
- **改期必须重置**：`reschedule` 成功后若新的 `starts_at` 距现在超过 24h/2h，清掉对应的已发送标记（否则新时间没提醒）。—— `create-appointment-transaction.md` §10 需补这一条。
- 取消/no_show/过期后：调度器天然跳过（状态不是 confirmed）。

## 3. 夜间窗口

- 21:00–08:00（门店时区）不发**提醒类**短信；到期落在窗口内的，08:00 后第一次 poll 发出。
- 确认/取消/改期类（用户动作直接触发的）**不受限**——客户刚点了取消，取消确认短信等到天亮是荒谬的。
- 邮件不受夜间窗口限制。

## 4. 渠道规则

- **SMS 主通道**：guest 预约本来就强制留手机号，覆盖率最高。发送方号码 v1 用一个 Groway 主号码；按店独立号码 v2。
- **Email 补充**：有邮箱才发；确认/取消/改期发，提醒不发。
- **退订**：`store.customer_sms_opt_out(phone TEXT PRIMARY KEY, opted_out_at)` ——收到运营商 STOP 回调即写。发送前查：命中 → 短信跳过，邮件照发；邮件也没有 → 记 log 不发。
- 每条短信带退订提示（模板 §5）。

## 5. 模板

模板 key 格式 `{event}.{channel}`，变量：`{store_name}` `{store_phone}` `{service_summary}` `{staff_name}` `{date}` `{time}` `{reference_code}`。

语言：`customer.language ?? booking_settings.notification_lang`（默认 `'en'`；v1 只做 `en`/`zh`）。

```
# booking.confirmed.sms
en: Hi {name}, your booking at {store_name} is confirmed: {service_summary} with {staff_name} on {date} at {time}. Ref {reference_code}. Call {store_phone} to change. Reply STOP to opt out.
zh: {name}您好，您在{store_name}的预约已确认：{date}{time}，{service_summary}（{staff_name}），预约号{reference_code}。改期请致电{store_phone}。回复 STOP 退订。

# booking.confirmed.email（subject）
en: Booking confirmed — {store_name}, {date} {time}
zh: 预约确认 — {store_name} {date} {time}

# reminder.24h.sms
en: Reminder: {store_name} tomorrow {time}, {service_summary} with {staff_name}. Ref {reference_code}. Need to change? Call {store_phone}.
zh: 提醒：您明天{time}在{store_name}有预约，{service_summary}（{staff_name}），预约号{reference_code}。改期请致电{store_phone}。

# reminder.2h.sms
en: See you soon! {store_name} today at {time}, {service_summary}. Ref {reference_code}.
zh: 期待您的光临！今天{time}，{store_name}，{service_summary}。预约号{reference_code}。

# booking.cancelled.sms
en: Your booking {reference_code} at {store_name} on {date} {time} has been cancelled. Hope to see you another time! {store_phone}
zh: 您{date}{time}在{store_name}的预约（{reference_code}）已取消，期待下次光临！{store_phone}

# booking.rescheduled.sms
en: Your booking has been moved to {date} {time} at {store_name}, {service_summary} with {staff_name}. New ref {reference_code}. Questions? {store_phone}
zh: 您的预约已改至{date}{time}，{store_name}，{service_summary}（{staff_name}），预约号{reference_code}。疑问请致电{store_phone}。

# booking.pending.sms（auto_confirm=false 的店 / payment_required 待支付）
en: Hi {name}, we received your booking request at {store_name} ({date} {time}). We'll confirm shortly. Ref {reference_code}.
zh: {name}您好，我们已收到您在{store_name}的预约请求（{date}{time}），稍后为您确认。预约号{reference_code}。

# booking.expired.sms
en: Hi {name}, your held slot at {store_name} ({date} {time}) has expired. Rebook anytime — we'd love to see you! {store_phone}
zh: {name}您好，您在{store_name}预留的时间（{date}{time}）已过期，欢迎重新预约！{store_phone}
```

- `{service_summary}`：单服务 = 服务名；多服务 = "A + B"（v1 取前两个 + "…" 防超长）。
- `{date}`/`{time}` 按门店时区排（`Oct 5` / `10月5日`，`2:30 PM` / `下午2:30`）。

## 6. 失败与重试

- 发送 worker：失败 → 指数退避重试（5m → 30m → 2h），3 次后标 `failed` 不再试。
- **提醒的特殊性**：如果重试时预约已开始（`starts_at < now()`），直接标 `failed` 跳过——迟到的提醒不如不发。
- 去重：`store.notification_log` 以 `(appointment_id, event_type, channel)` 唯一；outbox relay 重放时 `ON CONFLICT DO NOTHING`，**绝不**重发。

```sql
CREATE TABLE store.notification_log (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  appointment_id    UUID NOT NULL REFERENCES store.appointments(id),
  event_type        TEXT NOT NULL,   -- created/confirmed/cancelled/rescheduled/expired/reminder_24h/reminder_2h
  channel           TEXT NOT NULL CHECK (channel IN ('sms','email')),
  recipient         TEXT NOT NULL,   -- 手机号或邮箱
  template_key      TEXT NOT NULL,
  lang              TEXT NOT NULL,
  status            TEXT NOT NULL CHECK (status IN ('queued','sent','failed')) DEFAULT 'queued',
  provider_message_id TEXT,
  cost_cents        INT,             -- provider 回执，用于记账（§7）
  error             TEXT,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  sent_at           TIMESTAMPTZ,
  UNIQUE (appointment_id, event_type, channel)
);
```

## 7. 记账

- 每条发出的消息记 `cost_cents`（Twilio/SES 回执；回执没回来就 NULL，不阻塞）。
- 按 `store_id` 汇总可查（`appointment_id → store_id`），v1 只记账不分摊——费用走合伙人（既定），表是为以后"某店短信超多要谈"留的。
- 定价文档的免费/付费档**不含**短信额度承诺（v1 不提，避免把自己框死）。

## 8. 合规（CASL，加拿大）

- 预约确认/提醒属于**已有业务关系下的事务性消息**，不是 marketing，不要求 express consent——但每条短信仍带 STOP 退订并即时 honor（§4）。
- 绝不把客户手机号用于营销（AI 召回的触达是另一个 feature，另行取 consent，不在本篇）。
- 以上是工程理解不是法律意见；pilot 前合伙人找律师过一遍模板。

ALTER TABLE store.booking_settings

## 10. 测试用例

1. 下单 → 1 分钟内收到确认 SMS + Email，`notification_log` 两行 `sent`。
2. relay 重放同一事件 → `ON CONFLICT DO NOTHING`，客户只收到一次。
3. 预约在明天 09:00 → 今天 09:00 左右收到 24h 提醒（容忍 poll 间隔）。
4. 24h 提醒到期落在凌晨 02:00 → 08:00 后第一次 poll 发出，当天不提前、不跳过。
5. 创建后立即取消 → 只收到取消确认，之后**没有**提醒。
6. 改期到更远的日期 → 已发送标记被重置，新时间正常收到两次提醒。
7. 短信网关连挂 3 次 → `failed`，无第 4 次；log 里有 error。
8. 号码已 STOP → 短信跳过、邮件照发；都没得走 → log 一行，不抛错。
9. `auto_confirm=false` 的店下单 → 收到的是 pending 模板，不是 confirmed 模板。

## 11. 推迟

1. 客户自助改期/取消链接（"My Bookings" 文档）——有了链接后模板加 `{manage_link}`。
2. 按店独立短信发送号码 / sender ID。
3. 提醒时间的按店自定义（v1 固定 24h/2h + 开关）。
4. 员工侧通知（新预约提醒员工）——back-office 日历文档定。
5. no-show 后的关怀触达——归 AI 召回 feature，不在本篇。
