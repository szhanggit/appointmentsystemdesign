# Customer My Bookings（2026-09-29 v1 草案）

本地 spec，供 Claude Code 实现。**只存本地，不上 GitHub。**

定位：客户自助查单、取消、改期。前面三篇 deferred 到这里的事一次收完：transaction doc §12（guest 凭码自助）、reminders doc §11（模板里的 `{manage_link}`）、end-to-end §8（My Bookings）。

基线事实：
- 取消/改期的业务规则已在 `create-appointment-transaction.md` §10 定死（`cancel_threshold_hours`、原地改期、终态机）——本篇只定"客户是谁、怎么证明、调哪个口"，不另发明规则。
- 通知走 reminders doc 的事件管线（cancel/reschedule 本来就发事件）。
- 跨模块模式沿用既定架构：Customer Module 的路由，in-process 调 Store Module（同 Admin Module → Store Module 的 Contracts 模式）。

## 0. 本篇的裁决（先看结论）

1. **Guest 凭 `reference_code` + 手机号查单，不上短信 OTP**。理由：8 位码空间（36^8）枚举不动 + 限流；能看到的数据本来就是他自己的短信里有的。OTP 是 v2 的事。
2. **接口挂 Customer Module（`/api/customer/bookings`），数据仍在 store schema**，in-process 调过去。理由：population 路由归 Customer，数据主权归 Store，架构既定模式。
3. **客户侧取消/改期规则与员工侧完全一致**（同一 `cancel_threshold_hours`）。理由：一套规则，不制造"为什么店里能退我不能"的困惑。
4. **改期 UI 复用公开流程的 Step 3**（日期时间选择器），选好后调 reschedule。理由：不写第二套选时间 UI。

## 1. 身份与"我的单"

两种身份，两种查法：

| 身份 | 怎么证明 | 能看到 |
|---|---|---|
| 登录客户（CustomerSession） | session | `customer_id = 自己` 的所有预约（upcoming + 过去 12 个月） |
| Guest | `reference_code` + 预约上的手机号 | 仅这一单 |

- Guest 预约事后注册了账号：v1 **不自动关联**（手机号对上也不链）。理由：账号体系的合并/认领规则是客户档案文档的事，本篇不碰。
- 枚举防护：guest 查询接口按 IP + `reference_code` 限流；连续 5 次手机号不匹配 → 该 code 锁定 15 分钟。

## 2. 接口

### 2.1 登录客户的单列表

`GET /api/customer/bookings?scope=upcoming|past` — CustomerSession。

- `upcoming`：`status IN ('pending','confirmed')` 且 `starts_at > now()`，按时间正序。
- `past`：终态 + 已过的 confirmed，按时间倒序，限 50 条（v1 不做分页）。
- Customer Module in-process 调 Store Module 查（`customer_id` 过滤）。
- 返回字段同 back-office 列表（calendar doc §2），减去员工内部字段（无）。

### 2.2 Guest 单单查询

`GET /api/customer/bookings/lookup?reference_code=&phone=` — 公开，限流。

- 命中 → 返回该单（同 2.1 字段）；`reference_code` 不存在 → 404；手机号对不上 → 404（**不区分**哪种错，防枚举）。
- 成功后前端拿 `id` 调 2.3/2.4 时**每次都带** `reference_code` + `phone`（无 session 可保持）。

### 2.3 取消

`POST /api/customer/bookings/{id}/cancel` — CustomerSession，或 guest 参数（`reference_code` + `phone`）。

- 所有权校验：登录 → `customer_id` 匹配；guest → 该单的 `reference_code` + `guest_phone` 匹配。失败 → 404。
- 规则：transaction doc §10（`cancel_threshold_hours` 内 → `409 CANCEL_TOO_LATE`，文案"请致电 {store_phone}"）。
- 成功 → `cancelled` + 事件 → 取消确认短信（reminders doc 已有模板）。

### 2.4 改期

`PATCH /api/customer/bookings/{id}/reschedule` — 鉴权同 2.3。

- Body：`{ new_staff_id?, new_start }`（`new_start` 门店本地时间）。
- 服务端跑完整重校验 + 原地 UPDATE（transaction doc §10）；冲突 → `409 SLOT_TAKEN`。
- 同样受 `cancel_threshold_hours` 约束（逻辑上是退了重订）。
- 成功 → 事件 → 改期确认短信；reminders doc 的调度器标记按 §2 重置（新时间重新计时提醒）。

## 3. UI 流程

**单列表页**（`/bookings` 登录态 / guest 查单结果页）：
- Upcoming 分组（pending 的置顶 + "等店家确认" badge）、Past 历史分组。
- 每单：日期时间、店名、服务、员工、`reference_code`、状态 badge；pending 显示"等确认"，confirmed 显示[改期][取消]。

**取消**：点取消 → 二次确认（显示 threshold 文案，如"开始前 X 小时内需致电"）→ 调 2.3 → 成功变 cancelled 分组。

**改期**：点改期 → 复用公开流程 Step 3 的日期时间选择器（同一组件，`store_id/service_id/option_id` 从原单带）→ 选新时间 → 二次确认（old → new）→ 调 2.4。

## 4. 通知

- 取消/改期成功走已有 outbox 事件 → reminders doc 的 SMS + Email 模板**直接复用**，本篇不写新模板。
- Guest 查单页不展示完整手机号（`416-***-4567` 脱敏），防屏幕窥探。

## 5. 安全要点

1. 任何越权/不存在 → 404，不区分。
2. Guest 接口限流：IP 维度 10 次/分钟；单 code 5 次错 phone 锁 15 分钟。
3. 改期/取消的并发：exclusion constraint 兜底（transaction doc §5），客户和员工同时动同一单 → 一个赢。
4. `reference_code` 不进 URL（查单用 query 参数是例外——这是 guest 唯一的钥匙；登录态列表页 URL 不带任何标识）。

## 6. Schema 增量

**无**。字段全已存在。Customer Module 新增的是路由 + in-process client，不是表。

## 7. 测试用例

1. 登录客户看到自己的两单，看不到别人的（`customer_id` 隔离）。
2. Guest 输对 code + 错 phone 5 次 → 第 6 次（即使输对）被锁 15 分钟。
3. Guest 用 code A 的 phone 查 code B → 404。
4. threshold 内点取消 → `409 CANCEL_TOO_LATE`，单还在。
5. 改期到被占的时间 → `409 SLOT_TAKEN`，原单不动。
6. 取消后 24h 提醒不再发（调度器状态过滤）。
7. 改期到更远日期 → 提醒标记重置，新时间正常收到提醒。
