# Customer Records（2026-09-29 v1 草案）

本地 spec，供 Claude Code 实现。**只存本地，不上 GitHub。**

定位：客户档案——建档、查重、搜索、guest 预约的认领。收拢前文 deferred：calendar doc §9（客户搜索接口）、my-bookings §8（guest 与账号关联）。

基线事实：
- `customer.customers` 表归 Customer Module 所有；`store.appointments.customer_id` 是应用层引用（无跨 schema FK），可空；guest 预约存 `guest_*` 快照（transaction doc §12、§15）。
- 公开下单不强制建档（friction 最优先）；员工手工单需要"搜出来直接用"。
- 鉴权：`storeId ∈ caller.AuthorizedStoreIds`；本篇接口挂 Store Module（`store.customers` 读视图）或 Customer Module（写）——见 §3。

## 0. 本篇的裁决（先看结论）

1. **去重键 = 手机号（E.164 归一化），全局唯一**。理由：booking 流程里唯一必填的联系字段就是手机；邮箱选填靠不住。
2. **前台建档用 upsert，不用严格创建**。理由：客人已存在时弹 409 只会制造 friction 和重复档案；返回 `created: true/false` 让 UI 知道。
3. **搜索范围 = 本连锁**（有过本连锁预约的人），不是全平台。理由：连锁是 tenant 边界；跨连锁共享客户是 v2 的产品决策，不是 v1 的默认。
4. **Guest 预约的认领 v1 走人工**（员工点"关联到此客户"），不自动链。理由：自动链的误链代价（把 A 的单算到 B 头上）高于人工点的成本；试点单店人工够用。
5. **Transaction doc 的 guest 双轨保留**，本篇不动它。理由：`guest_*` 诚实记录了"下单时客人填了什么"，是审计来源；`customer_id` 是后来的关联。两列并存不冲突。

## 1. 数据模型

`customer.customers`（Customer Module 拥有，本篇只列 v1 需要的列）：

```sql
CREATE TABLE customer.customers (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  phone      TEXT NOT NULL UNIQUE,          -- E.164，如 +14161234567；去重键
  name       TEXT NOT NULL,
  email      TEXT,
  language   VARCHAR(5) NOT NULL DEFAULT 'en',  -- en/zh（reminders doc 用）
  notes      TEXT,                          -- 过敏、偏好等（前台可见）
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_customers_name_prefix ON customer.customers (name text_pattern_ops);
```

- 归一化规则：去空格/横杠/括号；`4161234567`（10 位）→ `+1…`；已有 `+` 直接存。归一化失败 → `400 INVALID_PHONE`。
- v1 **没有**生日/会员/储值列——那是 loyalty/marketing 的 v2。

## 2. 档案从哪来

| 来源 | 动作 |
|---|---|
| 员工手工建单时搜不到 | 表单里直接建（upsert），`customer_id` 回填到预约 |
| 员工在客户页点"新建" | 同上 |
| 公开 guest 下单 | **不建**（保持 frictionless）；`guest_*` 留痕 |
| 员工认领 | `POST .../claim` 把某条 guest 预约挂到档案下（§3.4） |

## 3. 接口

### 3.1 搜索

`GET /api/store/customers/search?store_id=&q=` — StoreSession，本连锁范围。

- `q` 匹配：归一化后 phone 精确，或 `name ILIKE 'q%'`（前缀）。
- 只返回**在本连锁有过预约**的客户（`EXISTS (appointments WHERE customer_id AND store in chain)`）——前台搜出来的人都是"来过的人"，减少误选。
- 返回：`id, name, phone（脱敏？不脱敏——前台要打电话，见 §5）, email, language`，限 20 条。

### 3.2 建档（upsert）

`POST /api/store/customers` — StoreSession（in-process 调 Customer Module 写）。

```json
// request
{ "store_id": "uuid", "name": "...", "phone": "...", "email": null, "language": "zh", "notes": null }
// response 200
{ "id": "uuid", "created": true }   // 已存在则 created: false，返回既有 id
```

- phone 归一化后 `ON CONFLICT (phone) DO NOTHING` → 查回既有行；**不**用新 name 覆盖旧名（前台手误改名是常见事故；改名走 PATCH）。
- 限流：防刷库（IP + store）。

### 3.3 更新

`PATCH /api/store/customers/{id}` — 改 `name/email/language/notes`。`phone` 本身**不许改**（改号 = 换人，走新建；防把 A 的档案改成 B 的号）。

### 3.4 认领 guest 预约

`POST /api/store/customers/{id}/claim` `{ "appointment_id": "uuid" }` — StoreSession。

- 校验：预约在本店、`customer_id IS NULL`（已关联的不重复认领 → `409 ALREADY_LINKED`)。
- 成功：`appointments.customer_id = id`（`guest_*` 保留不动——审计来源）。
- 出事件 `appointment.customer_linked`（下游预留，v1 无消费方）。

## 4. 权限矩阵

| 动作 | staff（本店） | store_admin | chain_admin |
|---|---|---|---|
| 搜索本连锁客户 | ✅ | ✅ | ✅ |
| 建档/更新 | ✅ | ✅ | ✅ |
| 认领预约 | 仅本店预约 | 本店 | 连锁内 |
| 看完整手机号 | ✅（工作需要） | ✅ | ✅ |

- 跨连锁搜不到（§0 裁决 3）；跨店在本连锁内可见（连锁即 tenant）。

## 5. 隐私要点

1. 前台能看到完整手机号是**工作需要**（打电话/发短信），但客户列表页默认脱敏（`416-***-4567`），点进详情才展开——防路过窥屏。
2. `notes` 只写服务相关（过敏、偏好），**不写**评价性内容。UI 占位符写明。
3. 导出客户名单：v1 不做（导出的每一份都是泄露面；要做走审批流，v2）。
4. 删除：客户要求删号 → 软删（`deleted_at`），预约历史保留（财务/审计需要，名字脱敏显示"已删除客户"）。

## 6. 测试用例

1. 同一手机号建两次 → 第二次 `created: false`，同一个 id，无重复行。
2. `416-123-4567` 与 `+14161234567` 建两次 → 同一档案。
3. A 连锁搜 B 连锁的客户 → 0 结果。
4. 认领已关联的预约 → `409 ALREADY_LINKED`。
5. 认领后 `guest_name` 还在，`customer_id` 已填。
6. 改 phone → `400`（不允许）。
7. 搜 `q=李` → 前缀命中，不命中中间字。

## 7. 推迟

1. Guest 自动关联（按 phone 自动链）——v2，先看人工认领的误操作率。
2. 档案合并（duplicates merge）——phone 去重后极少需要。
3. 客户自助改自己的档案（账号体系）。
4. 生日/会员/储值/积分字段（loyalty v2）。
5. 客户名单导出审批流。
